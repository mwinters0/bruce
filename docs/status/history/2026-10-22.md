## The `libstdc++` and `libgcc_s` call, answered

- **The maintainer's answer** to the one open entry (the release binary links
  `libstdc++` and `libgcc_s` dynamically): `v0.1.0-rc.1` is tagged now (it is
  published, 6.2 ticked), and the static build is tried afterwards, with
  `-static-libstdc++ -static-libgcc`, so the binary needs only glibc. The
  question, ship static or dynamic, is decided before `v0.1.0` (6.3) on what
  the attempt finds, and D23's "self-contained" wording is settled by that
  outcome. Release candidates exist to iterate the workflow.
- **It is out-of-band, M13, blocking P6**: it changes no decision the P6 spec
  records (the Trixie glibc floor, the workflow, the prerelease sequence) and
  fits one session, a build of about three minutes and a run on three images.
  An outcome that would change a spec decision goes back through grilling.
- **What the attempt finds**, to be written here when it lands: whether the
  build links with DuckDB's bundled C++, the size against rc.1's 60 MB binary
  and 19.7 MB archive, and whether it runs on `debian:trixie`, `fedora:44` and
  `fedora-minimal:42` as rc.1 did
  ([`../../wip/roadmap-P6.2-release-workflow-notes.md`](../../wip/roadmap-P6.2-release-workflow-notes.md),
  "The release, checked"). A static build ships as `v0.1.0-rc.2` and later
  tags, rc.1 being immutable.
- **6.3 inherits the outcome.** 6.2's notes say 6.3's README states that the
  binary links `libstdc++` and `libgcc_s` dynamically; that holds only if the
  attempt does not ship static, and the session landing M13 corrects the notes.

## M13 landed

- **Static, shipped.** `release.yml`'s Build step links `libstdc++` and
  `libgcc_s` in and fails on a binary whose `ldd` lists either; the call and the
  rejected linker arguments are D23's. `ldd` now lists `libm`, `libc` and the
  loader only; newest glibc symbol `GLIBC_2.38`, as rc.1.
- **The numbers**, in `debian:trixie` on 24 cores: build 2m47s to 2m52s;
  binary 60,827,280 bytes against 60,055,448 dynamic (+0.8 MB); archive
  19,988,678 bytes against rc.1's 19,690,968.
- **The run**: the workflow's steps rehearsed (`workflows.py script release.yml
  --skip "Check out the tag" --before Publish`, tag `v0.1.0-rc.2`, a copy of the
  tree committed in a scratch repo), then the archive unpacked and `bruce crawl
  http://127.0.0.1:8765/whole/` over `fixtures/antora/pages` printed `run 1: 40
  targets, 7 pages, no sitemap` and exited 0 in `debian:trixie` (after
  `ca-certificates`), `fedora:44` and `fedora-minimal:42`.
- **What was not tried**: a host with no `libstdc++` at all, `ldd` being the
  evidence there; a C++ exception crossing DuckDB's frames beyond what a crawl
  exercises. `v0.1.0-rc.2` is not tagged; every tag push is the maintainer's.
- Logs: `runs/release-static/` (`build-a.log`, `build-b.log` the two linker
  arguments that left it dynamic; `rehearsal.log` the shipped one).
- 6.3's README states glibc as the only library, per
  [`../../wip/roadmap-P6.2-release-workflow-notes.md`](../../wip/roadmap-P6.2-release-workflow-notes.md).
