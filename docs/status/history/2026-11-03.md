## Review of the `SHA256SUMS` call

- **Affirmed (maintainer):** `SHA256SUMS` keeps listing the latest digest under
  its fixed names. A puller's check may fail within Pages' ten minutes after a
  deploy, and a later run passes; only CI has the stale-cache guarantee. Naming
  the digest by content would not have given a puller CI's guarantee anyway: a
  same-day rerun rewrites a dated digest under its name, and a trim drops one that
  last night's `SHA256SUMS` still lists. Filed as D103's `Rejected` line. The
  spec's "The published directory is the contract" is amended to match.
- **The pull's `DEST` must persist between runs** (`docs/manual/deploy.md`,
  "Delivering the results"). docs.fp.o's build volume persists, and its language
  trees are replaced each run (the spec, "Facts the grilling found").

## Review of the CI workflow's YAML parse

- **Affirmed (maintainer):** `sim` reads the guide's workflow with `workflows.py`'s
  subset parser and `e2e` parses it as YAML; `scripts/` stays standard library
  only. Filed as D42's `Rejected` line; the spec's "The guide's new parts are
  executed, as its config is" and its 9.5 row are amended to match. The facts:
  `test_sim.ThisRepo` runs `sim.check_workflow` on the guide inside `unittest`,
  every `check` run; `e2e` runs at any change to `docs/manual/deploy.md`
  (`E2E_READS`), with Node pinned in `mise.toml`.
- **Admitted: M44.** This repo's own `release.yml` is read only by the subset
  parser, no YAML parser seeing it before GitHub does at a tag push. The
  maintainer chose `e2e`'s js-yaml check over every workflow, with
  `.github/workflows/` triggering `e2e`; rejected were a separate Node-only check,
  a Rust dev-dependency parser, and leaving GitHub's parse at the tag as the check.
  `release.yml` is one job, the shape `deployment.yaml_steps` asserts. It blocks
  nothing in P9; `go` picks it up after the open phase.
