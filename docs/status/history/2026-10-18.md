## The run's sitemaps are links from each root

- The maintainer settled P3.6's open call on "the run records that it had no
  sitemap" (`../../design/roadmap-P3-crawler.md`, "Sitemaps"): each root gets a
  link to each sitemap file it read.
- Why not "no `sitemap` link in the run": `targets` carries no kind
  (`src/store/schema.rs`), so a set or robots-named sitemap that is broken,
  unreadable or `too_large` is a target nothing links to and that links
  nowhere, indistinguishable from no sitemap; and the DB stores no roots,
  so a per-run answer is wrong for one root of a run where only the other
  has a sitemap. D14's unlisted-pages report needs the same per-root fact.
- Why not a `runs` column: schema 3 and an update D2 allows only for
  `finished_at`, and it is still per run and still names no broken file.
- The links are a new kind, `sitemap_file`, for root → file and index →
  child: today an index's children are `sitemap` links like a page entry
  (`src/crawl.rs`, `write_sitemap`), so a broken child and a broken page
  read alike. The source is the root's URL whatever named the file,
  robots.txt being no target; a file two roots share gets a link from each,
  docs.fp.o's `/fr/` and `/de/` sitemaps being byte-identical.
- The work is P3.6.1, earned by P3.6 shipping the wrong contract, and it
  precedes P3.7. D13, D47 and the P4 inbox's "What a crawl leaves for the
  join to place" keep describing today's code until it lands.
- **Pickup:** P3.6.1.

## A stop is bounded in time

- Reviewing P3.7's call on the first Ctrl-C, the maintainer amended the
  spec's "An interrupted run" (`../../design/roadmap-P3-crawler.md`): the stop
  is bounded at 30 s, a started target takes no further hop, retry or
  fallback, what is cut is left unwritten, and the second Ctrl-C still
  flushes the writer.
- Why: the old text's "the 30 s timeout bounds it" never held. A sent
  request is retried after 1, 2 and 4 s or a `Retry-After` of up to 60 s
  (`src/fetch/http.rs`, `Settings::default`, `HttpFetcher::get`), and every
  hop, retry and HEAD-then-GET fallback is admitted again
  (`HttpFetcher::once`), so a started target re-queues behind its host's
  pace after the stop. Up to 64 targets start at once (`crawl::WORKERS`);
  at `Crawl-delay: 1` the wait passed a minute. A long first stop invites
  the second press, which exited without flushing up to 4096 rows.
- Fewer targets in a stopped run costs a report nothing: the run is
  unfinished either way, and P4 reads the latest finished one by default
  (its inbox, "An interrupted crawl leaves an unfinished run").
- A target waiting for its host's place has reserved no pace slot
  (`Host::admit`, `src/fetch/http/host.rs`), so dropping one costs the host
  nothing.
- The shape settled for P3.7.1: each target's hops are dropped 30 s after
  the first Ctrl-C (D48); `follow` checks the stop before each hop,
  retry and fallback; and `HttpFetcher::once` races `admit()` against a
  stop handed to the fetcher, so a target still waiting for its host's
  place returns at once as stopped, while a sent request runs to the
  deadline. `host.rs` is untouched. Rejected: the deadline alone, a stop
  with 60 waiters at `Crawl-delay: 1` then always taking the full 30 s; and
  aborting at once, which drops responses half read.
- What the user sees: the first Ctrl-C prints `stopping: finishing requests
  in flight (30 s at most); Ctrl-C again to abandon them`, and the summary
  gains `, K cut` when K > 0; `docs/manual/crawl.md` says the same. The
  exit status stays 130.
- The work is P3.7.1, earned by P3.7 shipping the old contract, and it
  precedes P3.8, the live crawl being where a stop's wait would show.

## An abandoned run holds whole targets

- Reviewing P3.7.1's calls, the maintainer affirmed the per-target bound
  and the cut count (D48), and amended the spec's "An interrupted run"
  (`../../design/roadmap-P3-crawler.md`): the second Ctrl-C lets a target
  already being written finish before the writer is flushed.
- Why: the second press drops the crawl's future and finishes the writer
  without waiting for the blocking pool (`src/cli/crawl.rs`), so a target
  mid-`Shared::write` can have sent its target row and only some of its
  page's links. The same hazard was D48's reason against an abort in
  `drive`. An unfinished run is harmless to P4's default today, but the
  rows lie about the page.
- The wait is unbounded: at most `WORKERS` local writes, the writer
  draining meanwhile, else one blocked on a full channel never ends. No
  third press: a wedged DuckDB is a bug to fix, not route around.
- The work is P3.7.2, earned by P3.7.1, ahead of P3.8, which does not
  depend on it. The manual and the code describe P3.7.1's second press
  until it lands.
- **Pickup:** P3.7.2.
